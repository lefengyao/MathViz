# 设计记录

## 为什么单独做一个技能

已有的 `inline-visualizer` 负责「流程、架构、图表、界面」这类**示意**图，它对数学图无能为力：
没有坐标系变换、没有函数采样、没有 3D 投影、没有几何标注惯例。让它画 `y = x²` 的切线，
它会手算几个点，曲率和切线位置全靠感觉。

MathViz 的定位是**精确**：坐标、比例、投影、拓扑关系必须能验算。

两者边界：

| | inline-visualizer | MathViz |
|---|---|---|
| 流程图、架构图、组织图 | ✓ | ✗ |
| 界面稿、卡片、表单 | ✓ | ✗ |
| 函数曲线、向量场 | ✗ | ✓ |
| 立体几何、多面体 | ✗ | ✓ |
| 图论、哈斯图、自动机 | ✗ | ✓ |
| 装饰插画 | ✓ | ✗ |

## 为什么不用现成库

| 候选 | 为什么不选 |
|---|---|
| D3.js | 功能全但不解决数学问题：它给的是 `scaleLinear` 和 `path` 生成器，采样、断点、投影仍要自己写。核心 200KB 只用到 5%。 |
| mermaid | 只能画流程图类，不支持函数和 3D；且它是「生成文本→渲染」，无法精细控制单个图元的颜色和标注。 |
| KaTeX / MathJax | 解决公式排版，不解决作图。可以在图内标公式时按需引入，但不是主力。 |
| Three.js | 用于真实感渲染，教学立体图不需要光照和材质，反而增加复杂度。 |
| Desmos / GeoGebra | 是完整应用，无法内联进对话片段。 |

结论：**自己写一个 300~500 行的最小运行时**，只覆盖数学作图必要的操作。

## 关键决策

### 1. 坐标由代码算，不由模型算

模型手写 SVG 时最容易错的就是坐标。运行时的存在意义是让模型只写数学表达式：

```js
V.plot(x => x*x - 2)          // 而不是 50 个手算的 L 指令
S.box([0,0,0], [2,2,2])        // 而不是 8 个顶点 × 3 次投影
G.draw()                       // 而不是 5 个节点的手调坐标 + 边避让判断
```

这是「快」和「准」同时成立的唯一方式：少写 token，且不会算错。

### 2. 断点用像素距离，不用数值大小

`tan x` 在渐近线附近的值可以是 1e6，也可以只到 50。用「值超过阈值就断」必然漏判。
改成判断**相邻采样点的像素距离**：超过画布高度的 1.6 倍就断开。与函数的具体量级无关。

### 3. 3D 用正交轴测，不用透视

`pitch` / `yaw` 两个角度控制，z 轴始终竖直向上：

```
X = x·cos(yaw) − y·sin(yaw)
Y = x·sin(yaw) + y·cos(yaw)
screen = (cx + X·s, cy + (−Y·sin pitch − z·cos pitch)·s)
depth  = Y·cos(pitch) + z·sin(pitch)
```

默认 `yaw=-30, pitch=20` 得到「x 右下、y 右上、z 向上」的标准右手系画法，符合国内教材。

不用斜二测（cavalier）是因为它的变形太大，`x` 和 `z` 方向等长、`y` 方向压缩一半，
画出来的"正方体"在数值上不是正方体，容易误导。

### 4. 隐藏边靠外法线点乘相机方向

不用「投影后面积符号」判断（依赖顶点绕向的一致性，容易错），而是：

1. 用 Newell 法从面的顶点算外法线 `n`；
2. 相机方向 `cd = (sin(yaw)cos(pitch), cos(yaw)cos(pitch), sin(pitch))`；
3. `n · cd > 0` 即面朝相机；
4. 一条边若相邻的两个面都背向相机，画虚线。

这个判据与投影方式、与顶点排列顺序的细节无关，只要面的顶点是从外看逆时针排列。

### 5. 绘制顺序：面 → 虚线 → 实线

第一版把虚线和面一起按深度排序，结果虚线的隐藏边被半透明面盖住，几乎看不见。
教科书的画法是**隐藏边画在面上层**（视觉上"透视"到内部），所以最终顺序是：

1. 所有面按深度从远到近填充（半透明，0.3）；
2. 背向的边画灰色虚线；
3. 朝向的边画实线。

### 6. 图论：边避让放在路由层

边穿过别的节点是图论图最难看的错误。解法是每条边在绘制前检查：
如果线段到某个非端点节点的距离小于 `r + 10`，就改用二次贝塞尔绕开，偏移方向取
「远离被穿节点」的那一侧，偏移量 `r + 30`。

多重边复用同一套偏移逻辑（按序号均分角度），两套逻辑合并成一个 `route()` 函数。

分层布局加了重心排序（barycenter）：每一层按上一层相关节点的平均位置排序，迭代 4 次。
这是减少哈斯图交叉最有效的一步。

### 7. 文氏图区域标签用极坐标预设

七个区域（`a/b/c/ab/ac/bc/abc`）的位置不能靠用户调偏移，否则每张图都要试错。
做法是按圆心几何算好固定比例：

```
a   (−1.15, −0.18)    ab  (0, −0.82)     abc (0, 0.02)
b   ( 1.15, −0.18)    ac  (−0.62, 0.32)
c   ( 0,  1.32)       bc  ( 0.62, 0.32)
```

每个点都验算过「到三个圆心的距离」：在该在的圆内、不该在的圆外。

## 踩过的坑

| 坑 | 表现 | 根因 | 修法 |
|---|---|---|---|
| `V.angle` 半径单位错误 | 三角形图上角标注甩到坐标 (2975, −1599) | 默认 `r=26` 按像素设计，却直接加在数学坐标上 | `r / sx` 转成数学单位；`rightAngle` 同理 |
| 隐藏边被面盖住 | 立方体只有 9 条实线，没有虚线 | 虚线先画、面后画，被半透明填充覆盖 | 调整绘制顺序为 面 → 虚线 → 实线 |
| 文氏图 `C` 标签压在 A∩B 区 | 标签与数字重叠 | 集合名统一放在圆正上方，第三个圆的上方正好是交集区 | 第三个集合名改放圆下方，并把圆心整体下移 `0.115r` |
| 正六边形截面被压成一条线 | 1:3.4 的扁条 | 视角与截平面接近平行，投影压缩过度 | 实测四组视角，选 `yaw 26 / pitch 36` |
| 函数图两侧大片空白 | 曲线只占中间 1/3 宽 | 用了 `equal:true`，而 x/y 跨度与画布比例不匹配 | 函数图不用等比 |
| 图论箭头消失 | 边末端看不到箭头 | `arrowHead` 的尖端/尾部参数传反，箭头朝外 | 尖端在终点，尾端沿反向 |

## 没做的事

- **透视投影**：教学不需要，且会让"平行线不平行"，反而干扰判断。
- **隐式方程求根**：`x²+y²=4` 要转参数方程，`y²=x³−3x` 这类代数曲线暂不支持。
- **自动截面求解**：过三点的截面多边形理论上可算，但边界情况多（平行、顶点相交），
  不如让模型按几何直觉给顶点。
- **字体内嵌**：数学斜体依赖系统 serif，打包字体会让单文件涨到几百 KB。
